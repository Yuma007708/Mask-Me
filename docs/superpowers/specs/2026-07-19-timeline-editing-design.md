# タイムライン編集機能 設計書

作成日: 2026-07-19

## 目的

Mask-Me の編集画面に、動画編集アプリ相当のタイムライン編集機能を導入する。
カット編集（分割・削除・並べ替え）、複数動画クリップの連結、BGM 追加を、
既存のモザイク編集と**同一画面**で行えるようにする。

## 確定した要件

| 項目 | 決定 |
|---|---|
| カット操作 | 分割（スプリット）／不要部分の削除／順番の並べ替え |
| 素材追加 | 別の動画クリップ、BGM・音声 |
| 速度変更 | **対象外**（時間軸を線形に保つ） |
| モザイクとの関係 | 同一画面で両方を編集する |
| 解像度・向きの差 | 先頭クリップに合わせ、他はアスペクト比を保って黒帯で収める |
| BGM と元音声 | 両方鳴らし、それぞれ音量を調節できる |

## アーキテクチャ

### 全体像

現在の「ソース動画1本」を、**クリップの列**に置き換える。

```
[Clip A: 素材1 の 0.0–3.2s] [Clip B: 素材1 の 5.8–9.0s] [Clip C: 素材2 の 0.0–4.1s]
                    ↓ AVMutableComposition で連結
        1本の連続した時間軸（= 従来の「動画1本」に相当）
                    ↓
        AVPlayer（プレビュー） / AVAssetReader（書き出し）
```

`AVMutableComposition` は `AVAsset` のサブクラスであるため、プレビューの
`AVPlayerItem` も書き出しの `AVAssetReader` も、合成結果を1本の動画として
そのまま扱える。これにより既存のモザイク描画・書き出し経路の大半を温存できる。

### 検出キャッシュのキー再設計（本設計の中核）

現在の `detectionCache` は `[Double: [FaceLandmarkSet]]` で、キーは
合成後の時刻を 15fps バケットに丸めた値である（`MosaicEditorModel.swift:88, 687`）。

この設計のままクリップ編集を導入すると、**クリップを1つ削除・並べ替えただけで
後続クリップの時刻が全てずれ、検出済みの顔情報が全て無効になる**。
プリスキャンをやり直すことになり、体験として成立しない。

したがってキーを「素材内の時刻」に変更する。

```swift
struct DetectionCacheKey: Hashable {
    let sourceID: UUID   // 素材（AVAsset）の識別子。クリップIDではない
    let bucket: Double   // その素材内での時刻（15fps バケット）
}
```

キーを**クリップIDではなく素材IDにする**点が重要である。同じ素材を分割して
2つのクリップになった場合、両者は同じ素材の検出結果を共有できる。
分割・削除・並べ替えのいずれでも検出結果は一切失われない。

顔ランドマークの座標も素材基準（正規化座標）で保持し、
解像度合わせによる黒帯・スケーリング変換は**描画時にのみ**適用する。

### 時刻の変換層

合成時刻と素材時刻の相互変換を一箇所に閉じ込める。

```swift
struct TimelineMapping {
    func sourceTime(at compositionTime: Double) -> (sourceID: UUID, time: Double)?
    func compositionTime(sourceID: UUID, time: Double) -> Double?
}
```

`lookupFaces(at:)` をはじめとする既存の時刻ベース API は、この変換層を
経由して素材時刻に直してからキャッシュを引く。呼び出し側の構造は変えない。

### データモデル

```swift
struct TimelineClip: Identifiable {
    let id: UUID
    let sourceID: UUID          // 素材の識別子
    var sourceRange: ClosedRange<Double>  // 素材内の使用範囲（秒）
    var originalAudioVolume: Float        // 元音声の音量
}

struct AudioTrack: Identifiable {
    let id: UUID
    let url: URL
    var startTime: Double       // 合成時間軸上の開始位置
    var volume: Float
}
```

`MosaicEditorModel` は `clips: [TimelineClip]` と `audioTracks: [AudioTrack]` を持ち、
これらの変更のたびに `AVMutableComposition` を再構築する。

### 既存 `trimRange` の扱い

現在の `trimRange`（書き出しの頭出し・尻切り）は、クリップ編集で表現できるため
**フェーズ2完了時に廃止する**。既存の下書きデータとの互換のため、
読み込み時に `trimRange` を単一クリップの `sourceRange` へ変換する移行処理を入れる。

## 実装フェーズ

各フェーズは単独で動作する状態を保ち、完了条件を満たしてから次に進む。

| # | 内容 | 完了時に得られるもの |
|---|---|---|
| 1 | クリップモデル導入、Composition 経由化、キャッシュキー再設計 | 見た目は現状のまま、内部が新基盤に移行。既存機能の回帰がないことを確定させる |
| 2 | 分割・削除・並べ替えの UI | カット編集が使える。`trimRange` を廃止 |
| 3 | 複数クリップの追加 | 動画をつなげる。先頭クリップの規格に合わせ黒帯で収める |
| 4 | BGM トラックと音量スライダー | 音声編集が使える |
| 5 | 区間モザイク（顔ごとの時間区間指定） | 選んだ区間だけモザイクをかけられる |

### フェーズ1の位置づけ

フェーズ1は成果が画面に現れない。「何も変わっていないように見えるが内部が
入れ替わっている」状態を経由する。ここで既存のモザイク品質を落とさないことを
検証しきることが、後続フェーズの前提になる。

単一クリップの場合も必ず Composition を経由させ、
特別扱いの分岐を作らない（分岐は必ず腐るため）。

**変換層の配線はフェーズ1では行わない（2026-07-19 改訂）。**
フェーズ1には素材全体を使う単一クリップしか存在しないため、
`TimelineMapping.sourceLocation(at:)` は恒等変換にしかならない。
にもかかわらず、これを配線するとアプリで最も品質を作り込んできた
検出・追跡経路を差し替えることになる。得るものがゼロで回帰リスクだけが最大である。

キー再設計の目的である「クリップ編集をしても検出結果が失われないこと」は、
**キーを `(素材ID, 素材内時刻)` に変えるだけで達成される**。
変換層が意味を持つのはクリップが複数になるフェーズ2以降であり、
配線もそこで行う。`TimelineMapping` 自体はフェーズ1で実装・テストしておく。

### フェーズ5の要件（既に確定済み）

- 顔ごとに別区間を持つ（グローバルな区間ではない）
- 1つの顔が複数区間を持てる
- 区間が空の顔はモザイクをかけない
- 動画読み込み直後は区間なし（素顔）から開始する

区間が空＝素顔のまま書き出される仕様のため、**書き出し前に
「区間が設定されていない顔があります」と警告する**。仕様は変えないが、
プライバシーアプリとして事故を防ぐ導線を置く。

## 各フェーズの完了条件

以下をすべて満たすこと。

1. **テスト** — 新規・更新テストを書き、実行して**テストケース数まで確認する**。
   過去にビルドキャッシュが古く「TEST SUCCEEDED なのに新規テストが1件も
   走っていない」事故があったため、成功表示のみを根拠にしない。
2. **ビルドと SwiftLint** — シミュレータビルドと lint を通す。
   `file_length` 500 行、`type_body_length` 300 行の制約を守る。
3. **サブエージェントによる厳格レビュー** — 差分をレビューさせ、
   指摘が出たら修正して再レビューする。
4. **実機確認** — プレビューと書き出しの目視確認。
   フェーズ1は特に「モザイク品質が劣化していないこと」を確認する。

### テスト方針

- 時刻変換層（`TimelineMapping`）は純粋な計算のため、単体テストで網羅する。
  分割・削除・並べ替えの各操作後に、素材時刻が保存されることを検証する。
- キャッシュキー再設計の回帰テストとして、
  「クリップを削除しても検出結果が失われない」ことを明示的に検証する。
- **`SAMPLE_VIDEO_DIR` は設定しない。**
  `SampleFalsePositiveTests` / `DiagLivePathDumpTests` / `DValidLiveModelTests` は
  実行しない（参照先の素材を扱わない方針のため）。

## リスク

1. **アプリの性格が変わる。** Mask-Me は「顔を隠す」単機能アプリとして
   完成度を高めてきた。動画編集機能の追加はテスト範囲・UI・競合の前提を変える。
   リリース時期は後ろ倒しになる（許容済み）。
2. **フェーズ1の回帰リスクが最も高い。** 検出キャッシュ・追跡層・
   書き出し経路という、これまで品質を作り込んできた部分の土台を差し替える。
3. **既存の下書きデータとの互換。** `trimRange` の移行処理を怠ると、
   保存済みの下書きが壊れる。

## 本設計の対象外（別課題として記録）

競合調査で判明したリリース上の課題。本設計には含めず、
タイムライン刷新の完了後に着手する。

| 項目 | 状況 | 重要度 |
|---|---|---|
| StoreKit 実接続 | `Entitlements.swift:17-28` が常に `isPro = true` を返すスタブ | 高（リリースブロッカー） |
| EXIF・メタデータ除去 | 未実装。顔を隠しても撮影場所が残りうる | 高 |
| 共有シート導線 | Photos 保存のみ。SNS 投稿前処理の導線が欠落 | 高 |
| `PrivacyInfo.xcprivacy` | 未作成 | 高 |
| ローカライズ（最低 en） | 日本語ハードコード | 高 |
| 黒塗り（完全塗りつぶし） | 未実装。モザイクは復元リスクがあり書類用途に不適 | 高 |
| 書類マスキングのプリセット | 未実装。日本市場での差別化候補 | 中 |

### 体・首・肩への誤モザイク（別途、単独で取り組む）

`.claude-handoff.md:601, 989-993` に既知課題として残る検出精度の問題。
本設計とは**意図的に分離する**。タイムライン刷新と混ぜると、
モザイク位置の変化が「検出精度の改善によるもの」か
「キャッシュキー再設計の回帰」かを切り分けられなくなるため。

刷新の完了後、この課題だけに集中して取り組む。
